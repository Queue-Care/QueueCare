## How the choices support Member 1's requirements

Public REST discovery supports hospital search and OPD selection (FR-08/FR-09). Confirm Appointment sends only a session ID with the patient's token. The backend determines the patient identity, validates current eligibility, reserves capacity and creates a unique booking plus its notification in one transaction. Unique patient/session and booking-code indexes support FR-10, FR-11 and FR-12. Notification failure rolls back the booking and capacity change, avoiding a partially completed confirmation. See the [transaction sequence](ARCHITECTURE.md#booking-transaction-sequence).

The UI separates loading, empty, unavailable and error states, supports explicit refresh, and prevents repeat submission while a booking is pending. Unknown network outcomes are not presented as successful bookings. These choices support understandable recovery; they are not a substitute for usability observations. [Booking integration](../CONFIRM_APPOINTMENT.md) and [accessibility checks](../ACCESSIBILITY.md) record the implementation and its limits.

## Current deviations and validation boundary

- Patient registration creates active accounts; the current login path also activates legacy pending-verification patients after a correct password. Do not describe this as completed verification-code authentication.
- The target patient queue refresh interval in the README is approximately five seconds. The implemented staff/Alerts intervals above differ, and patient queue integration remains pending.
- Cloudinary is the planned external media service, but the actual server includes a MongoDB fallback. Its image read route uses an unguessable URL and is public to anyone holding that URL; it is not a JWT-protected image download.
- Opening hours are an optional extension to the original hospital schema. The API displays stored text; fictional demo hours are not verified real hospital data or session availability.

No tests were rerun for this documentation-only task.
